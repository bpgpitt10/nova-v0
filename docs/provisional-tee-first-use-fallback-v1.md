# First-use provisional tee fallback — isolated Live Caddie implementation

**Branch:** `provisional-tee-live-fallback-v1`, derived from `auto-aim-windows-companion-v1`. **Production:** unchanged. **Scope:** first-time start when an imported hole has no trustworthy mapped or locked tee for the golfer's selected tee set; do not rebuild the recommender, hole progression, OSM surfaces, Windows Companion, or shot archive.

## Purpose

A never-before-played imported course must provide some first-shot guidance, even when OSM does not contain the physical tee polygon for the user's selected Blue/White/etc. tee. Until the true GSPro-to-OSM transform is validated, the fallback **cannot** claim that the displayed marker is the real tee; users should see its uncertainty and a warning that precise carries / hazard margins / tee elevation are unverified. Some holes cannot safely support even this approximation.

**Eligibility:** a precisely locked tee or unique selected named OSM tee always wins. If the course geometry is already verified in a selected-tee frame, do not degrade it with this fallback; if the nearest mapped tee anchor was chosen only approximately and the selected tee color is unmapped, a provisional estimate is legitimate.

**Why the earlier proposed screen-X mapping is not valid:** the ball's horizontal fraction of a GSPro minimap depends on camera centering, zoom, view rotation and clipping. Neither minimap X nor relative ball-to-waypoint pixel direction is independently tied to OSM north/east or local right/forward. Mapping “30% from the left” into a synthetic OSM tee box would invent lateral coordinates. This implementation uses observed pixels for the **straight ball-to-pin distance** only; it does not silently pretend to recover lateral position.

## Algorithm, with existing ownership preserved

1. `src/courseGeometry/liveSupportedTee.ts` continues to prioritize the *active round's selected tee set*, one matching imported tee candidate, and a previously **locked** tee calibration. If a mapped/locked tee exists, no provisional algorithm changes it.
2. For missing selected tees on an approximate imported map, `src/courseGeometry/provisionalTeeEstimate.ts` takes the existing base tee marker and green polygon centroid. The base marker may be the raw OSM hole route start **or a nearest mapped tee anchor chosen by the existing coordinate normalization**, but neither is assumed to identify the golfer's selected tee. If either is absent, the hole has invalid route geometry, or the map registration is unavailable, it declines to invent a tee.
3. With no fresh GSPro ball/pin ruler, use that already-existing map anchor as a provisional initial tee **planning hypothesis**; expose a 50-yard **heuristic planning guard band**, not a measured 50-yard positional accuracy claim. This preserves the existing Start Round Hole 1 / shot 1 behavior without re-opening hole detection.
4. When `LiveCaddiePage` sees an active provisional first-shot state and a connected Windows Companion, it requests **one** read-only native observations snapshot per hole/round, using the existing native marker detection + gray-waypoint OCR scale. If the user has Native Wind/Lie already enabled, reuse those observations instead. The native snapshot must have fresh ball + pin markers, positive scale derived from credible native waypoint/par-3 ruler, ball near the bottom of the tee minimap, and matching course identity or explicit manual Hole 1 context. **Do not reuse previous-hole coordinates as live ball position.**
5. The true **straight** GSPro ball-to-pin yards are estimated from `ballPixel`, `pinPixel`, `yardsPerPixel`. Project this *scalar distance* onto the existing OSM route-start-to-green-centroid axis, taking the OSM green-center-vs-real-flag discrepancy as uncertainty. This produces a longitudinal adjustment only. If the measured straight distance differs from that OSM baseline by more than **45 yards**, **block the calculated adjustment** instead of forcing a match. A refined candidate has a **25-yard heuristic planning guard band** but remains provisional.
6. The existing Live Caddie worker and risk engine receive the proposed ball position. No fake tee `CourseSurface` polygons are introduced; all OSM/LiDAR geometry stays in the same coordinate frame. `LiveCaddieMap` paints a dashed uncertainty circle around the ball for Shot 1, plus a warning about approximate carries, hazards and elevation. Native aim is still disabled. The uncertainty radius is **not** a statistical confidence interval and is not used to declare any forced carry safe.
7. Subsequent **real physical shots** continue to come from the existing browser GSPro course state and archived `currentRound.dat`. `src/adapters/browserGsproCourseArchive.ts` already extracts `StartingPOS` and `EndingPOS` into `rawMetrics.startingPositionMeters`/`endingPositionMeters`; `src/lib/liveGsproRoundArchive.ts` already persists `raw_metrics` to `live_course_shots` in Supabase. Do not duplicate physical shot ingestion or accidentally lock a synthetic tee. In the future, after verified GSPro-to-OSM mapping, compare recorded first-shot `StartingPOS` to provisional position and enroll confirmed tee sets in a shared course-calibration cache.

## Safety and known remaining limitations

- This does **not** solve exact first-use physical tee latitude/longitude. It is a bounded practical fallback on route-start geometry, not a substitute for the full GSPro `teePos/pinPos` layout extraction and robust course-wide OSM transform.
- No trusted camera scale: existing OSM route-start or approximate mapped tee anchor stays broad. No greens or bad geometry: no new tee point. A >45-yard distance mismatch cannot be used to refine the tee. This prevents a false correction, but the uncorrected route start may also be wrong: check the explicit warning.
- Left/right tee offsets, separate tee decks, large par-3 tee setbacks and some sharp doglegs cannot be resolved from a scalar distance; errors may be **larger than 25 or 50 yards**. Those numerical bands are **planning heuristics**, not certified spatial error limits.
- The current recommender does **not yet marginalize outcomes over that full possible tee area**. Its one-ball-point evaluation is preliminary. Never claim hazard-edge precision, guaranteed safe carries, approved map geometry, exact tee elevation or automatic aim from this fallback.
- The companion's old `currentRound.dat` records may still be stale at tee changes; the existing manual Start Round and hole-progress logic remain authoritative. No extra hole state parser, OCR hole detector, memory inspection, Windows EXE installer change, production course promotion or shared tee-cache release in this pass.

## Test and acceptance

- `node tools/test-provisional-tee-live-fallback.mjs`: valid route-start estimate, native scalar distance adjustment, >45-yard rejection, mapped/locked tee priority, stale/invalid/non-independent marker scale rejection and no native aim/lock authorization. Run through Web Alpha CI on the isolated branch alongside existing native preview, hazard/OSM and TypeScript build checks.
- **Physical sim check:** use a route-imported runtime-ready course with a hole **missing a matched tee set**, even if it has other mapped tee pads and select a tee set before Start Round. On Hole 1 verify immediate provisional tee + circle **before** first shot; if Companion connected, wait for a single native snapshot and verify “GSPro ball/pin ruler constrained” versus “OSM route start only.” Compare rough distance visually with GSPro; record the tee, adjustment and coordinate assumptions. Hit first shot and confirm the normal GSPro archive still saves `raw_metrics.startingPositionMeters` and shot progression. Repeat after advancing to the next hole. Never enable aim clicking. **A simulator result is still needed before calling this fallback field validated.**

**Separate next milestone:** extract GSPro's full per-course layout `teePos/pinPos`, cross-check with multiple OSM greens, fit and validate one geographic transform, and reuse validated tee coordinates across users. That solves the underlying precise tee problem; this fallback is for holes still lacking that evidence.


## Superseding FarmLinks field results / next implementation — 2026-10-13

The earlier 45-yard route-only restriction and Greywolf-specific post-shot transform did **not** produce a playable FarmLinks White tee: actual ~493 yd versus default ~572 yd, OSM Tee 3 ~495 yd. The Companion saw ball/pin but failed both 445/253 gray waypoint ovals; after one drive GSPro and Looper correctly reported Shot 2 / ~263 yd, but the Looper course-local ball remained at tee and the recommender offered Driver. The existing Chrome round parser saves the first-shot GSPro StartingPOS, but imported courses have no registered post-shot map projection. This is a known failed end-to-end acceptance, not completion.

**Authoritative replacement:** follow the priority and acceptance gates in `docs/windows-companion-autoaim-execution-plan-v2.md` section **CURRENT PRIORITY — Unified imported-course live positioning**. Use observed straight-to-pin distance to rank **all** available OSM tee candidates, provisionally prefer a uniquely strong mapped match, fall back to a broad approximate tee when uncertain, use one validated generic course-frame transform for subsequent physical ball movement, and suppress spatially precise recommendations when current position is unregistered. Do not equate White with Tee 3 permanently; the user's actual tee name remains authoritative. No native click and no broad 18-hole coordinates project as a prerequisite.
